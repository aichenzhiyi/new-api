# 项目功能介绍

> 整理日期：2026-11-23；更新日期：2026-11-24。本文依据当前工作区的 New API 源码和已确认的业务需求整理，是二次开发功能清单；文档中的“待新增”“待修改”不代表已经完成开发。“已有”表示源码提供相应基础能力，具体供应商、模型和部署版本仍需联调验收。

## 一、项目定位与建设范围

本项目基于 [QuantumNous/new-api](https://github.com/QuantumNous/new-api) 二次开发，建设公司内部的算力标准化平台。第一期聚焦“大模型统一接入、模型信息管理、Token 用量统计、估算成本和外部采购额度管理”。

已确认的业务前提：

- 公司主要通过业务系统/API 使用模型，可以将调用统一切换到本平台。
- 需要接入 GPT、千问、豆包等不同厂商的模型。
- 用量和估算成本需要按部门、项目统计，管理维度到项目为止，不建设应用与环境管理，第一期不做强制预算拦截。
- 系统账号面向项目管理人员；账号关联项目后即可管理和查看该项目，不设置项目内角色或分级权限。同一账号可关联多个项目。
- 公司直接在供应商官网充值，平台不收款，但需要人工登记充值并管理额度。
- 第一期不建设 GPU、CPU、内存、显存等硬件资源监控，也不建设服务器调度和模型部署系统。

主要调用流程：业务系统持有项目关联的平台凭证 → 请求统一网关 → 网关选择模型服务渠道 → 调用上游 → 记录用量与估算成本 → 汇总部门、项目报表。

平台只能够直接统计经过自身的调用。供应商账户存在平台外消耗时，必须通过人工校准或后续账单同步核对余额。ChatGPT、豆包等官网聊天产品的使用量不属于此次 API 统计范围。

## 三、业务对象与归属关系

| 对象 | 业务含义 | 当前状态与处理 |
| --- | --- | --- |
| 模型 | 具体模型及版本、厂商、能力、适用场景 | 已有模型目录，待补充企业管理字段 |
| 渠道/服务接入点 | API 地址、上游模型标识、地域、凭证及路由配置 | 已有，可复用并关联供应商账户 |
| 供应商账户 | 公司实际采购和充值的账户 | 待新增企业账户台账；现有厂商元数据不能替代采购账户 |
| 额度池 | 实际共享余额或资源包的范围 | 待新增，可被一个或多个模型、渠道共同使用 |
| 部门 | 用量统计与费用承担主体 | 已开发，待数据库实测；目前仅全局管理员维护，项目关联后续实施 |
| 项目 | 一项业务建设或使用活动 | 待新增，指定费用承担部门、业务负责人及关联管理账号；负责人用于业务联系，不形成额外权限级别 |
| 平台调用凭证 | 业务系统访问本平台的 API Key | 已有，待直接绑定项目 |
| 管理用户 | 登录平台管理和查看项目的人员 | 已有，待增加所属部门及项目关联；项目内管理权限一致 |
| 用户与项目关联 | 账号可以管理和查看的项目范围 | 待新增，用户与项目为多对多关系，不设置项目角色字段 |

默认关系为“部门 → 项目 → 多个调用凭证”。每个调用凭证直接关联一个项目，同一项目可持有多个凭证，调用用量统一归属项目及其费用承担部门。跨部门项目一期指定一个费用承担部门，不做跨部门自动拆账。业务系统使用项目调用凭证，员工使用管理账号；不建立应用和环境实体。

创建管理账号时设置所属部门并关联可管理的项目，也可以在项目管理中由平台管理员维护关联账号。关联同一项目的账号均可管理该项目的业务信息、项目调用凭证，并查看用量、成本、日志及导出数据，不再区分项目负责人、普通成员、只读等权限角色。所属部门用于人员组织管理，不自动授予该部门全部项目的访问权；用户所属部门不决定调用费用归属。

平台管理员保留全局管理权限，负责账号与项目关联、全局配置和跨项目共享资源；项目管理权限不等于原系统的全局管理员权限。项目管理人员不能自行扩大可管理项目范围。项目内角色简化不影响服务端项目隔离，账号只能访问其关联项目；共享渠道、供应商账户和额度池不能仅因关联某项目就向该项目所有管理人员开放全局修改权。

已有 Group 参与模型访问、路由和计价，不直接改作部门。公司组织关系应建立独立实体。

统计口径要求：

- 优先使用上游返回的 usage；估算和缺失单独标识，缺失不等于零。

- 本地模型未设置核算规则时显示“成本未核算”，不能默认为免费。

### 4.4 外部充值与额度管理（本次新增重点）

当前项目有渠道余额查询和平台用户额度调整，但没有满足上述场景的完整供应商外部充值台账。用户充值订单、人工补单及用户额度调整均不能直接替代此功能。

#### 额度登记示例

以下为同一人民币现金额度池的示例，不适用于直接将金额与 Token 数相减：

| 项目 | 金额 |
| --- | ---: |
| 基准时点登记余额 | ¥500 |
| 基准时点之后登记的官网充值到账 | +¥2,000 |
| 同期平台估算消耗 | -¥300 |
| 当前平台估算剩余 | ¥2,200 |

现金额度池的一般计算口径：有效基准余额 + 基准后实际到账及其他有效增加 - 基准后估算消耗 - 退款及其他有效减少。校准后的计算从新基准时点开始，不再次累加已包含的历史流水。

#### 额度业务规则

1. **充值归属以供应商实际规则为准。** 若 2,000 元仅属于一个模型，建立专属额度池；若多个模型共享一个账户余额，只记一笔共享额度，模型页面展示关联，不能重复累计。
2. **实际支付与到账额度分开。** 优惠、赠送、退款独立记录；现金余额、赠送金、Token 资源包不能混为同一单位，不能简单相加。
3. **充值记录与官方余额快照分开。** 人工登记充值后，官方同步到的余额是核对快照，不能再次当作充值增加。
4. **估算余额与官网真实余额分开。** 平台外调用、供应商价格差异和结算延迟可能造成差异。无可靠数据时显示未知或待核对，不冒充实时余额。
5. **Token 资源包单独核算。** 明确模型、地域、有效期、输入/输出扣减及耗尽后规则；不能直接按现金价格换算得到确定 Token 额度。
6. **余额台账不直接改变内部用户额度。** 两类额度分别管理，避免供应商充值被误记为用户钱包充值。
7. **模型或渠道停用不删除历史账目。** 同一供应商账户关联多个渠道时，也不能重复汇总余额或消耗。

## 八、二次开发注意事项

1. **许可证与署名。** 当前仓库采用 AGPLv3，并有 NOTICE 附加要求。保留规定署名、原项目链接、New API 和 QuantumNous 项目信息。内网部署也不能直接推定没有源码提供义务；闭源要求在开发前确认许可方案。

6. **前端复用与国际化。** 复用现有业务组件和图表，新增页面文案遵循项目 i18n 规范，金额及数字使用统一格式化工具。
7. **统计与计价。** 遵循项目 billing 规则；不把用户收费倍率、平台内部额度和供应商成本混用。计价表达式变更另行阅读表达式设计文档并验证相关边界。
8. **数据留存与运行验证。** 约定日志保留期、备份、聚合和恢复策略；不能仅凭编译或渠道连通测试宣称计量、成本和余额核对正确。

## 十一、二次开发功能排期

| 项目 Token 统计 | 部门 01 → 项目 02 → 账号与项目隔离 03 → 项目 Key 与归属明细 05 → 聚合统计 06 | 没有项目身份和调用归属，只增加一个项目筛选框不能得到可信统计 |
| 企业成本报表 | 实际用量 05/06 + 采购账户 04 + 价格依据 09 | 不能直接将原平台用户扣减额度当成企业采购成本 |
| 外部充值登记 | 供应商账户 04 → 额度池及权限 07 → 流水、防重复与冲正 08 | 必须确定给谁增加额度、谁能操作，以及如何避免重复记账 |
| 估算剩余额度 | 期初与充值 08 + 对应采购成本 09 → 余额及校准 10 | 只登记充值无法得出当前余额；还需明确基准时点与同期消耗 |
| 对外开放项目报表与导出 | 项目数据权限 03 + 归属/聚合 05/06 + 对应页面权限校验 11 | 项目内权限相同不代表可以访问其他项目；不能先开放数据再补隔离 |
| 资源包消耗与剩余 | 额度池 07 + 分类用量 05/06 + 资源包规则 Q09 | 先确定适用模型、输入/输出抵扣规则与有效期；自动抵扣是否实施按采购规则确认，未实现时仅展示台账及人工核对结果 |
| 官方余额同步与预警 | 余额台账与校准 10 + 厂商接口权限确认；到期提醒还依赖资源包台账 | 同步值作为官方快照核对，不能重复当作充值；预警要基于明确来源及更新时间 |

在满足各自前置条件后，供应商/额度台账与用量统计的部分工作可以分别推进。例如批次 07、08 不依赖项目 Token 报表完成，但批次 10 必须等待成本链路完成。表中顺序是默认执行顺序，不要求没有依赖的工作相互等待。

### 11.4 验证与交付要求

1. 每批交付时同步更新功能状态；尚未完成的功能保持“待新增/待修改”，代码已实现但真实数据库验证尚未完成时标记“已开发，待数据库实测”，不因页面完成就标记整体验收通过。
2. 涉及数据库的批次按项目要求运行真实 SQLite、MySQL、PostgreSQL 验证，覆盖新建、升级与迁移幂等；影响日志路径时验证受影响的独立日志数据库。
3. 组织关联、项目隔离、Key 改绑、历史归属、跨项目导出和共享资源操作随相关批次做回归；金额变动覆盖并发、重复登记、冲正及校准不重复入账等行为。
4. 用量采集、价格记录、成本和余额功能分别核对数据，再做完整流程验证；补算必须能够避免重复累计，不能将原明细与聚合结果相加作为总消耗。
5. 前端改造复用现有组件、完成国际化和受影响检查；原平台的计量、额度检查、结算及已有报表需要做兼容回归。
6. 第六章的 GPU/CPU 监控、自动账单对账、预算硬限制和部署调度等保持后续阶段，不混入本次一期排期。

P0 完成后的核心交付链路为：建立部门和项目 → 创建并关联管理账号 → 创建项目 Key → 业务调用并记录 Token → 查看项目成本 → 登记官网充值并核对估算余额。P1 增强项的完成情况单独列出，不掩盖 P0 未完成事项。

- **字段与关系**：项目全局唯一编码、名称、费用承担部门、业务负责人、说明、启停状态及创建/更新时间；编码统一大写，名称 1–64 字符，负责人最多 64 字符，说明最多 255 字符，时间列按 `YYYY-MM-DD HH:mm:ss` 显示。每个项目必须选择一个费用承担部门，跨部门项目同样明确一个承担部门，不再额外建立参与部门、应用、环境、费用归属字段或项目角色。业务负责人是联系信息，不授予账号权限。
