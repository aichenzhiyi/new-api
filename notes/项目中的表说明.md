# 项目中的 MySQL 表说明

整理日期：2026-11-23。依据当前工作区源码整理，适用于本版本的 New API；后续版本增加或删除模型时，需要同步更新本文。

本文说明每张表保存什么、由哪些功能读写，以及主要业务关系。关键字段用于帮助理解业务，不替代完整 DDL。未连接运行中的 MySQL，实际实例中的列类型、索引和历史遗留表应以 `SHOW CREATE TABLE` 为准。文中的源码链接相对于本文件所在的 `notes/` 目录。

## 1. 表清单的来源和数据库归属

### 1.1 如何确认哪些结构体会建表

不能把所有 Go 结构体都当成数据库表。本次核对了以下入口，并排查了生产代码中的 `AutoMigrate`、`CreateTable`、`CREATE TABLE`、`TableName()` 和显式表查询：

- [model/main.go](../model/main.go)：`InitDB`、`migrateDB`、`InitLogDB`、`migrateLOGDB`。主库的批量迁移清单包含 36 个模型，MySQL 路径另外迁移 `SubscriptionPlan`。
- [model/audit_log.go](../model/audit_log.go)：`MigrateAuditLogs` 迁移 `AuditLog`。
- [model/option_primary_key_migration.go](../model/option_primary_key_migration.go)：配置表修复时会创建临时表，并保留旧表备份。
- [model/gorm_logger.go](../model/gorm_logger.go)：`newGormConfig` 没有设置自定义全局表名前缀或单数表策略。默认采用 GORM 的蛇形命名与复数规则，有 `TableName()` 的模型使用显式表名。

据此识别出 **38 个固定表名**。其中 `casbin_rule` 是显式指定的单数表名，`quota_data` 是 GORM 命名规则下的实际表名；不要自行改写为 `casbin_rules` 或 `quota_datas`。条件迁移产生的 `options_pk_tmp` 和 `options_legacy_<时间戳>` 不计入这 38 个固定表名，另见第 9 节。

### 1.2 主库和日志库

| 场景 | 数据库连接 | 表的归属 |
|---|---|---|
| 未配置 `LOG_SQL_DSN` | `SQL_DSN` 指向的主库；`LOG_DB = DB` | 38 个固定表名均在同一个 MySQL 库中迁移 |
| 配置独立 MySQL 日志库 | `DB` 使用 `SQL_DSN`，`LOG_DB` 使用 `LOG_SQL_DSN` | 主库迁移 37 个表名，日志库迁移 `logs`、`audit_logs` |
| 主库 MySQL、日志库为其他引擎 | 主库仍使用 MySQL，日志表通过对应日志引擎访问 | 不应把日志库中的对象一律称作 MySQL 表 |

**一个容易误判的细节：** 当前 `migrateDB` 的主库清单始终包含 `Log`。因此，分离日志库后，主库中仍可能存在一个 `logs` 表，而正常日志读写使用的是 `LOG_DB` 对应的 `logs`。若主库和日志库是两个不同的 MySQL 库，38 个固定表名会对应合计 39 个表实例：主库 37 个，日志库 2 个。

迁移通常由主节点执行，`NODE_TYPE=slave` 跳过主要建表迁移。表已创建不代表已经有业务数据：例如未启用 Passkey、订阅或插件时，相应表可以为空。切换日志库连接也不等于程序会自动搬迁历史日志。

## 3. 用户、令牌、登录与权限

### 3.1 `users`：用户账户主表

- **含义与关键内容：** 保存用户名、密码哈希、显示名、角色、状态、邮箱、第三方账号标识、所属 `group`、钱包 `quota`、累计 `used_quota`、请求次数、邀请关系、个人 `setting` 和认证版本 `auth_version`。
- **写入位置：** [controller/user.go](../controller/user.go) 的注册与用户管理；[controller/setup.go](../controller/setup.go) 的首次管理员创建；[model/user.go](../model/user.go) 的 `Insert`、`Edit`、`Update`；额度预扣、结算和充值也会修改该表。
- **读取位置：** [middleware/auth.go](../middleware/auth.go) 的用户状态与分组检查；[model/user_cache.go](../model/user_cache.go) 的用户缓存；用户管理列表、个人资料和钱包等页面。
- **主要关系：** 被 `tokens.user_id`、`user_sessions.user_id`、订单、订阅、日志和任务等业务字段引用。`inviter_id` 是邀请人用户 ID。
- **边界：** `OriginalPassword`、`VerificationCode`、`AdminPermissions` 等带 `gorm:"-:all"` 的字段不落库；`access_token` 是遗留面板访问令牌字段，不等同于模型 API Key。用户删除包含软删除路径。

### 3.2 `tokens`：模型 API Key

- **含义与关键内容：** 保存模型调用令牌、名称、用户 ID、状态、过期时间、剩余额度、累计消费、是否无限额度、调用分组、自动分组配置、模型白名单和 IP 限制。
- **写入位置：** [controller/token.go](../controller/token.go) 的 `AddToken`、更新和删除；[model/token.go](../model/token.go) 的 `Insert`、`SelectUpdate`、`IncreaseTokenQuota`、`DecreaseTokenQuota`；[model/quota_reserve.go](../model/quota_reserve.go) 的 `TryReserveTokenQuota`。
- **读取位置：** [middleware/auth.go](../middleware/auth.go) 的 `TokenAuth` 调用 `ValidateUserToken`；[middleware/distributor.go](../middleware/distributor.go) 读取模型访问限制；令牌管理页面读取令牌列表。
- **主要关系：** `user_id → users.id`；`logs.token_id`、`tasks.private_data` 中的令牌关联及 `quota_data.token_id` 用于追踪用量。
- **边界：** `group` 指定路由使用的分组，但仍需通过账号可用分组检查。`auto_groups` 是该表内的文本配置，不是独立关联表。包含软删除字段。

### 3.3 `user_access_tokens`：管理 API 个人访问令牌

- **含义与关键内容：** 保存个人访问令牌的哈希、显示提示、名称、权限范围 `scopes`、过期时间、最近使用时间和 IP。它与调用 `/v1/chat/completions` 的 `tokens` 分工不同。
- **写入位置：** [controller/access_token.go](../controller/access_token.go) 创建、修改、删除令牌；[model/user_access_token.go](../model/user_access_token.go) 的 `CreateUserAccessToken`、`UpdateUserAccessToken`、`TouchUserAccessToken`。
- **读取位置：** [middleware/auth.go](../middleware/auth.go) 的个人访问令牌查找与验证；[service/access_token_scope.go](../service/access_token_scope.go) 的管理 API 权限范围处理；账户访问令牌列表。
- **主要关系与生命周期：** `user_id → users.id`；[service/auth_cleanup.go](../service/auth_cleanup.go) 调用过期记录清理。数据库字段 `token_hash` 不保存可直接使用的原始令牌。

### 3.4 `user_sessions`：网页登录会话

- **含义与关键内容：** 以 `sid` 为主键，保存用户 ID、会话版本、用户认证版本、活跃或撤销状态、当前与上一份刷新凭证哈希、有效期、登录方式及设备上下文。
- **写入位置：** [service/auth_session.go](../service/auth_session.go) 创建登录会话、刷新、退出及撤销；[model/user_session.go](../model/user_session.go) 的 `CreateUserSession`、`RotateUserSessionRefresh`、各类 `Revoke...` 操作。
- **读取位置：** 面板认证、活跃会话列表和刷新请求通过 `GetUserSessionCached` 等函数读取。
- **主要关系与生命周期：** `user_id → users.id`；会话版本与 `users.auth_version` 共同参与有效性判断；过期和旧撤销记录由 [service/auth_cleanup.go](../service/auth_cleanup.go) 清理。Redis 是缓存，不替代该表。

### 3.5 `auth_flows`：临时认证流程状态

- **含义与关键内容：** 保存流程令牌哈希、`purpose`、提供商、操作意图、用户、会话、流程载荷、到期时间和消费时间。
- **业务场景：** OAuth state、TOTP 登录、Passkey 登录或注册、登录二次验证、安全操作证明、邮箱绑定、Telegram 断言以及插件登录流程。具体类别由 `AuthFlowPurpose...` 常量区分。
- **写入与读取：** [model/auth_flow.go](../model/auth_flow.go) 的 `CreateAuthFlow`、`GetAuthFlow`、`ConsumeAuthFlow`、`ConsumeAuthFlowWithAction`；调用者包括 [controller/oauth.go](../controller/oauth.go)、[controller/login_verification.go](../controller/login_verification.go)、[service/auth_token.go](../service/auth_token.go) 和 [service/passkey/session.go](../service/passkey/session.go)。
- **生命周期：** 某些流程与用户和当前会话绑定，消费或到期后不能作为新的有效流程继续使用；过期记录由认证清理任务删除。`payload` 是流程内部数据，不能当成普通日志公开。

### 3.6 `external_identity_claims`：外部身份归属

- **含义与关键内容：** 保存 `provider + subject + user_id` 的身份归属。唯一约束分别限制同一外部身份的拥有者，以及用户在同一提供商下的身份槽位。
- **当前使用范围：** 当前模型代码明确接入的是 Telegram；不能据表名推断所有内置 OAuth 绑定都已迁移到这张表。
- **写入与读取：** [model/external_identity_claim.go](../model/external_identity_claim.go) 的 `ClaimExternalIdentityWithTx`、`ReleaseExternalIdentityWithTx`、`GetUserByTelegramID`、`BindTelegramForSessionWithTx`；Telegram 登录和绑定路径使用这些方法。
- **主要关系与迁移：** `user_id → users.id`，与 `users.telegram_id` 的相关操作协同；启动时 `InitializeExternalIdentityClaims` 从旧 Telegram 绑定回填归属记录。

### 3.7 `passkey_credentials`：Passkey 凭证

- **含义与关键内容：** 保存用户 ID、RP ID、凭证 ID、公钥、签名计数、认证器信息、备份状态、传输方式和最近使用时间。服务器保存的是凭证公钥等验证材料，不是用户设备上的私钥。
- **写入位置：** [controller/passkey.go](../controller/passkey.go) 和 [model/passkey.go](../model/passkey.go) 的注册、更新断言状态及删除操作。
- **读取位置：** Passkey 登录、账户安全验证、凭证状态展示；[service/passkey/user.go](../service/passkey/user.go) 将持久化记录转换成 WebAuthn 用户凭证。
- **主要关系：** `user_id → users.id`；当前 `user_id` 有唯一索引，不能按通用 WebAuthn 的多凭证设计推断该表允许每用户任意多条有效记录。包含软删除字段。

### 3.8 `login_encryption_keys`：登录请求加密密钥

- **含义与关键内容：** 保存 `slot` 和 `private_key_pem`，用于网页登录密码请求的服务端解密。它不是密码哈希表，也不是渠道服务商密钥表。
- **写入与读取：** [model/password_crypto.go](../model/password_crypto.go) 的 `InitPasswordEncryption` 查询或创建 `active` 槽位，并加载到 [common/password_crypto.go](../common/password_crypto.go) 对应的密码加密功能中。
- **使用入口：** [main.go](../main.go) 在启用登录密码请求加密时初始化；浏览器获取公钥和提交加密密码时使用已加载的密钥材料。
- **主要约束：** `slot` 唯一，多个副本通过该槽位共享同一份持久化密钥。该表包含服务端私钥材料。

### 3.9 `two_fas`：TOTP 双因素认证

- **含义与关键内容：** 保存用户的 TOTP secret、是否启用、失败次数、锁定截止时间、最近使用时间等。`TwoFA` 按 GORM 默认规则命名为 `two_fas`。
- **写入与读取：** [model/twofa.go](../model/twofa.go)、[model/twofa_enrollment.go](../model/twofa_enrollment.go)；[controller/twofa.go](../controller/twofa.go) 提供设置、启用和停用功能，[service/twofa.go](../service/twofa.go) 参与验证码验证。
- **主要关系与流程：** `user_id → users.id` 且唯一。设置中的认证状态可由 `auth_flows` 关联，验证完成后再启用；登录和敏感操作会读取启用状态。包含软删除字段。

### 3.10 `two_fa_backup_codes`：双因素认证备用码

- **含义与关键内容：** 保存用户 ID、备用码哈希、是否已使用及使用时间；不保存供用户直接复制使用的备用码明文。
- **写入与读取：** [model/twofa.go](../model/twofa.go) 的 `replaceBackupCodesWithTx`、`ValidateBackupCode`、`GetUnusedBackupCodeCount`；[controller/twofa.go](../controller/twofa.go) 的备用码生成和账户验证功能。
- **主要关系与生命周期：** `user_id → users.id`，与该用户的 `two_fas` 配置共同使用；备用码使用会更新状态，重新生成会替换原记录。包含软删除字段。

### 3.11 `custom_oauth_providers`：自定义身份提供商

- **含义与关键内容：** 保存提供商名称、slug、是否启用、Client ID / Secret、授权和 Token 端点、用户信息端点、Scopes、字段映射、OIDC discovery 地址及访问策略。
- **写入位置：** [controller/custom_oauth.go](../controller/custom_oauth.go) 的提供商管理，通过 [model/custom_oauth_provider.go](../model/custom_oauth_provider.go) 的创建、更新和删除方法持久化。
- **读取位置：** [oauth](../oauth) 下的自定义提供商加载与处理、登录方式展示、OAuth 回调和用户绑定管理。
- **主要关系：** `user_oauth_bindings.provider_id → custom_oauth_providers.id`；内置 GitHub 等提供商的配置不一定在本表，部分使用 `options` 和 `users` 中的专用字段。

### 3.12 `user_oauth_bindings`：自定义 OAuth 账号绑定

- **含义与关键内容：** 保存本站用户 ID、提供商 ID、提供商用户标识和绑定时间。
- **写入与读取：** [model/user_oauth_binding.go](../model/user_oauth_binding.go) 的 `CreateUserOAuthBindingWithTx`、`GetUserByOAuthBinding`、`UpdateUserOAuthBinding`、`DeleteUserOAuthBinding`；[controller/oauth.go](../controller/oauth.go) 和 [controller/custom_oauth.go](../controller/custom_oauth.go) 的登录、绑定、解绑及列表功能。
- **主要约束：** `user_id + provider_id` 唯一；`provider_id + provider_user_id` 唯一，分别表达“用户在一个提供商的一份绑定”和“该提供商身份的一位本站拥有者”。

### 3.13 `authz_roles`：管理权限角色定义

- **含义与关键内容：** 保存角色 key、显示名、说明、是否内置、启用状态和排序。当前内置角色包括 Root 和 Admin。
- **写入位置：** [service/authz/seed.go](../service/authz/seed.go) 的 `seedBuiltInRoles` 在权限初始化时写入或更新内置角色。
- **实际使用边界：** 当前生产代码主要对本表执行启动时的内置角色写入；没有找到把本表任意记录读取为动态角色定义的业务查询。[service/authz/role.go](../service/authz/role.go) 的角色展示来自代码中的 `builtInRoles`，不能仅靠手工往表里新增一行获得一个可用角色。模型定义见 [model/authz_role.go](../model/authz_role.go)。
- **角色关系：** 用户的系统角色仍在 `users.role`；当前角色归属由 [service/authz/assignment.go](../service/authz/assignment.go) 根据系统角色推导，没有额外的用户—角色关联表；实际权限策略由 `casbin_rule` 持久化。

### 3.14 `casbin_rule`：具体权限策略

- **含义与关键内容：** 保存 Casbin 的 `ptype`、`v0` 至 `v5`。当前主要规则中，`v0` 是主体，`v1` 是资源，`v2` 是动作，`v3` 是 allow / deny 效果；其余字段还参与旧策略兼容处理。
- **主体示例：** `role:admin` 表示角色权限，`user:<用户ID>` 表示单用户覆盖。不是模型路由使用的 `VGS` 等业务分组。
- **写入与读取：** [service/authz/adapter.go](../service/authz/adapter.go) 的 `LoadPolicy`、`SavePolicy`、`AddPolicy`、`RemovePolicy`；[service/authz/seed.go](../service/authz/seed.go) 初始化角色基线；[service/authz/override.go](../service/authz/override.go) 保存用户权限覆盖。
- **使用入口：** 管理 API 的资源权限检查、渠道操作授权、插件和审计日志等管理权限。模型定义 [model/casbin_rule.go](../model/casbin_rule.go) 显式指定单数表名。

## 4. 渠道、模型与系统配置

### 4.1 `channels`：上游渠道

- **含义与关键内容：** 保存渠道类型、名称、上游凭证、基础地址、状态、模型列表、支持分组、优先级、权重、模型映射、请求头与参数覆盖、渠道设置、测试耗时、余额和累计用量。
- **写入位置：** [controller/channel.go](../controller/channel.go) 的渠道管理；[controller/channel-test.go](../controller/channel-test.go) 和 [controller/channel-billing.go](../controller/channel-billing.go) 更新测试和余额信息；[model/channel.go](../model/channel.go) 的 `Insert`、`Update`、`UpdateChannelUsedQuota` 等方法。
- **读取位置：** [middleware/distributor.go](../middleware/distributor.go) 的渠道上下文设置；[service/channel_select.go](../service/channel_select.go) 的渠道选择；[relay/compatible_handler.go](../relay/compatible_handler.go) 和各提供商适配器读取配置后请求上游。
- **主要关系：** `abilities.channel_id`、`logs.channel_id`、`tasks.channel_id`、`quota_data.channel_id` 等引用渠道。`channel_info`、`setting`、`settings` 是同表中的结构化配置，不是独立表。

### 4.2 `abilities`：分组—模型—渠道路由关系

- **含义与关键内容：** 用 `group + model + channel_id` 联合主键，表达某个渠道能为哪个分组提供哪个模型，并保存启用状态、优先级、权重和标签。
- **写入位置：** [model/ability.go](../model/ability.go) 的 `AddAbilities`、`UpdateAbilities`、`DeleteAbilities`；新增或更新渠道时，依据渠道模型列表与分组列表生成组合记录。
- **读取位置：** `GetChannel`、`GetGroupEnabledModels`；[model/channel_cache.go](../model/channel_cache.go) 构建分组、模型、渠道的内存索引；模型列表、定价页和模型关联渠道查询也会读取能力数据。
- **业务示例：** “阿里百炼-VGS”支持 `VGS` 和 `qwen3.8-27b`，会形成对应的能力记录。API Key 使用 `VGS` 时，在通过用户授权检查后，按 `VGS + qwen3.8-27b` 找可用渠道。
- **边界：** 这里的 `model` 是模型名称字符串，不是 `models.id` 的外键；给模型增加目录资料不等于已经有可路由渠道。

### 4.3 `models`：模型目录资料

- **含义与关键内容：** 保存模型名称或匹配规则、说明、图标、标签、厂商 ID、端点说明、同步设置、状态和软删除信息。
- **写入位置：** [controller/model_meta.go](../controller/model_meta.go)、[model/model_meta.go](../model/model_meta.go) 的 `Insert`、`Update`、`DeleteModelMetadata`；[model/model_metadata_sync.go](../model/model_metadata_sync.go) 参与模型资料同步。
- **读取位置：** 模型管理、模型广场、定价展示，以及 [controller/model.go](../controller/model.go) 的模型信息补充；结合渠道能力展示模型可用情况。
- **主要关系与边界：** `vendor_id → vendors.id`；`BoundChannels`、`EnableGroups`、`QuotaTypes`、`MatchedModels` 等是运行时或响应字段，不是额外的数据表。模型价格不应简单理解为保存在本表。

### 4.4 `vendors`：模型厂商资料

- **含义与关键内容：** 保存厂商名称、说明、图标、状态和时间，用于模型资料分类与展示。
- **写入与读取：** [controller/vendor_meta.go](../controller/vendor_meta.go)、[model/vendor_meta.go](../model/vendor_meta.go)、[model/vendor_management.go](../model/vendor_management.go) 提供增删改查及关联处理；模型管理与定价展示读取厂商信息。
- **主要关系：** `models.vendor_id → vendors.id`。它不是上游渠道凭证表；多个渠道可以访问同一厂商的模型，不能把厂商和渠道视为一一对应。

### 4.5 `prefill_groups`：预填集合

- **含义与关键内容：** 保存名称、类型、JSON 数组 `items`、说明及软删除信息；用于复用模型、标签、端点等集合。
- **写入与读取：** [controller/prefill_group.go](../controller/prefill_group.go) 提供 `/api/prefill_group/` 管理接口；[model/prefill_group.go](../model/prefill_group.go) 的 `Insert`、`Update`、`GetAllPrefillGroups` 保存和读取集合。
- **边界：** 本表是表单预填资料，不是用户所属分组，也不是 API Key 的路由分组。不要用它解释 `users.group` 或 `tokens.group` 的授权关系。

### 4.6 `options`：系统配置

- **含义与关键内容：** 以 `key` 为主键，`value` 保存配置值；值可能是布尔、数字、文本或序列化 JSON。
- **写入位置：** [controller/option.go](../controller/option.go)、[model/option.go](../model/option.go) 的 `UpdateOption`、`UpdateOptionsBulk`；模型价格和分组等专门管理入口也会调用配置写入。
- **读取位置：** 启动时 `InitOptionMap`、`LoadOptionsFromDatabase` 加载配置；[setting](../setting) 下各设置对象和业务服务使用已加载的配置；多节点配置同步会触发重新加载。
- **典型业务：** 模型价格配置、分组倍率、可用分组、站点开关、邮件与支付配置、部分插件和请求处理配置。实际 key 以 [model/option.go](../model/option.go) 及相应设置模块为准。
- **边界：** `pricing*.go`、`model_pricing*.go` 多为价格读写与视图逻辑，不意味着存在同名的 `pricing` 或 `model_pricings` 表。环境变量也不都会写入本表。

### 4.7 `setups`：首次初始化状态

- **含义与关键内容：** 保存初始化时的版本号和初始化时间。
- **写入位置：** [controller/setup.go](../controller/setup.go) 的 `PostSetup`；[model/main.go](../model/main.go) 的 `CheckSetup` 在存在 Root 用户但缺少记录的兼容场景下补建记录。
- **读取位置：** [model/setup.go](../model/setup.go) 的 `GetSetup`，用于启动初始化判断和初始化页面。
- **边界：** 不是每次数据库迁移的版本账本；不能用这张表的记录数推断执行过多少次迁移。

## 5. 钱包、充值、兑换与订阅

### 5.1 `top_ups`：钱包充值订单

- **含义与关键内容：** 保存用户、充值数量、支付金额、交易号、支付方式和提供商、创建与完成时间、订单状态。
- **写入位置：** [model/topup.go](../model/topup.go) 的订单 `Insert`、各支付渠道的 `Recharge...`、`ManualCompleteTopUp`；[controller](../controller) 下的 `topup*.go` 处理发起支付及回调。
- **读取位置：** 个人钱包充值记录、管理员订单列表和搜索，通过 `GetUserTopUps`、`GetAllTopUps` 等方法查询。
- **主要关系与流程：** `user_id → users.id`；充值完成事务更新订单状态和用户钱包，之后记录充值日志。交易号用于识别订单；`amount` 与 `money` 分别承载项目定义的数量和金额，不能直接混用为同一单位。

### 5.2 `redemptions`：额度兑换码

- **含义与关键内容：** 保存兑换码、创建者、名称、额度、状态、创建与兑换时间、实际兑换用户和过期时间。
- **写入与读取：** [controller/redemption.go](../controller/redemption.go) 管理兑换码；[model/redemption.go](../model/redemption.go) 的 `Redeem` 在兑换时检查状态并更新用户额度；钱包充值入口调用兑换功能。
- **主要关系与边界：** `user_id` 对应创建者，`used_user_id` 对应兑换用户；包含软删除字段。`Count` 用于批量创建请求，带 `gorm:"-:all"`，不是持久化列。

### 5.3 `checkins`：每日签到

- **含义与关键内容：** 保存用户 ID、签到日期 `YYYY-MM-DD`、奖励额度和创建时间。
- **写入与读取：** [controller/checkin.go](../controller/checkin.go) 的状态查询与签到入口；[model/checkin.go](../model/checkin.go) 的 `UserCheckin`、`HasCheckedInToday`、`GetUserCheckinRecords`、`GetUserCheckinStats`。
- **主要关系：** `user_id → users.id`；`user_id + checkin_date` 唯一，避免同一天重复签到。签到奖励同时影响用户钱包，金额规则来自签到设置。

### 5.4 `subscription_plans`：订阅套餐定义

- **含义与关键内容：** 保存套餐名称、说明、售价与币种、有效时长、可用额度、重置周期、购买限制、是否可用钱包支付、订阅耗尽后是否允许使用钱包、购买后升级分组及到期降级分组，以及外部支付商品 ID。
- **写入位置：** [controller/subscription.go](../controller/subscription.go) 的管理员套餐创建、更新及状态操作；模型定义与默认值归一化在 [model/subscription.go](../model/subscription.go)。
- **读取位置：** 用户套餐列表、订阅购买、创建用户订阅、订阅周期重置；`GetSubscriptionPlanById` 及套餐缓存提供读取。
- **主要关系：** `subscription_orders.plan_id`、`user_subscriptions.plan_id` 指向套餐。套餐定义与用户已经获得的订阅实例不是同一份记录。

### 5.5 `subscription_orders`：订阅购买订单

- **含义与关键内容：** 保存用户、套餐、金额、交易号、支付渠道、状态、创建和完成时间，以及支付提供商载荷。
- **写入与读取：** [controller/subscription.go](../controller/subscription.go) 和 `controller/subscription_payment_*.go` 发起支付及处理回调；[model/subscription.go](../model/subscription.go) 的 `GetSubscriptionOrderByTradeNo`、`CompleteSubscriptionOrder`、`ExpireSubscriptionOrder` 查询和变更订单。
- **主要关系与流程：** `user_id → users.id`，`plan_id → subscription_plans.id`；支付完成后创建实际的 `user_subscriptions`。订阅订单与钱包充值订单 `top_ups` 分开存储。

### 5.6 `user_subscriptions`：用户订阅实例

- **含义与关键内容：** 保存用户、套餐、总额度和已用额度、起止时间、状态、来源、重置时间，以及购买时有关升降组和钱包回退的配置快照。
- **写入位置：** [model/subscription.go](../model/subscription.go) 的 `CreateUserSubscriptionFromPlanTx`、`PreConsumeUserSubscription`、`PostConsumeUserSubscriptionDelta`、`ResetDueSubscriptions`、`ExpireDueSubscriptions`；管理员也可绑定或调整用户订阅。
- **读取位置：** 用户订阅页面、管理端用户订阅列表、[service/funding_source.go](../service/funding_source.go) 的订阅计费来源；[service/subscription_reset_task.go](../service/subscription_reset_task.go) 处理重置和到期维护。
- **主要关系与并发：** `user_id → users.id`，`plan_id → subscription_plans.id`；额度变更使用事务与行锁保护。它承担实际消费余额，不能通过修改套餐展示价格来代替更新订阅实例。

### 5.7 `subscription_pre_consume_records`：订阅请求预扣记录

- **含义与关键内容：** 保存唯一请求 ID、用户、实际订阅 ID、预扣额度和 `consumed / refunded` 状态。
- **写入与读取：** [model/subscription.go](../model/subscription.go) 的 `PreConsumeUserSubscription` 创建或复用预扣记录，`RefundSubscriptionPreConsume` 按请求 ID 处理退款；[service/funding_source.go](../service/funding_source.go) 的 `SubscriptionFunding` 调用这些方法。
- **主要关系与用途：** `user_subscription_id → user_subscriptions.id`；请求 ID 使预扣和退款可识别同一次请求，防止重复退款。最终差额结算还会更新订阅实例，不能把预扣值直接当作最终扣费金额。
- **生命周期：** [service/subscription_reset_task.go](../service/subscription_reset_task.go) 调用 `CleanupSubscriptionPreConsumeRecords` 清理满足条件的历史记录。

## 6. 日志、审计与统计

### 6.1 `logs`：逐请求与额度变动日志

- **含义与关键内容：** 保存用户、时间、类型、模型、令牌、渠道、输入输出 Token、扣费额度、耗时、是否流式、使用分组、请求 ID、上游请求 ID、说明 `content` 和扩展元数据 `other`。
- **写入位置：** [model/log.go](../model/log.go) 的 `RecordConsumeLog`、`RecordErrorLog`、`RecordTopupLog`、`RecordTaskBillingLog` 等，最终通过 `createLog → LOG_DB.Create` 写入；调用者包括 [service/text_quota.go](../service/text_quota.go)、[service/relay_error.go](../service/relay_error.go) 及任务结算代码。
- **读取位置：** [controller/log.go](../controller/log.go) 的全部与本人日志、统计和导出；模型方法包括 `GetAllLogs`、`GetUserLogs`、`SumUsedQuota`。常见接口为 `/api/log/`、`/api/log/self`。
- **关系与边界：** `user_id`、`token_id`、`channel_id` 关联主库对象，但部分名称和分组是当时的日志快照。`ChannelId` 对应物理列 `channel_id`，虽然 JSON 字段叫 `channel`；`channel_name` 的来源还包括运行时补充。
- **正文存储：** 普通聊天请求默认不会把完整 `messages` 和完整模型回答写入本表；`content` 是日志说明或失败原因。此前为排障添加的上游响应打印进入进程运行日志，不是自动写入这张表。
- **类型与维护：** 常量包括未知、充值、消费、管理、系统、错误、退款和登录；当前新增登录和相关管理安全事件主要走 `audit_logs`，历史 `logs` 仍可能存在旧类型。`DeleteOldLogBatch` 按截止时间删除本表历史记录，不会连带删除所有聚合与任务数据。

### 6.2 `audit_logs`：操作与安全审计

- **含义与关键内容：** 保存事件 ID、用户、事件发生时操作者角色、类别、动作、访问令牌指纹、认证方式、IP、User-Agent、方法、路由、状态码、成功标记、请求 ID、说明和结构化审计信息。
- **写入位置：** [model/audit_log.go](../model/audit_log.go) 的 `RecordAuditLog`；[model/log.go](../model/log.go) 的登录和操作审计封装；[middleware/audit.go](../middleware/audit.go) 的审计中间件以及相应控制器。
- **读取位置：** [controller/audit.go](../controller/audit.go) 与 `GetAuditLogs`，供 `/api/audit`、`/api/audit/self` 及审计日志页面使用。
- **主要关系与归属：** 用户 ID 关联 `users`；`token_ref` 是指纹引用，不是模型令牌表主键。通过 `LOG_DB` 读写，可与主库分离；迁移入口是 `MigrateAuditLogs`。
- **边界：** 不是模型回答正文表，也不是 `logs` 的子表；历史审计记录的存在不应依赖用户当前是否仍有相同角色。

### 6.3 `quota_data`：看板用量聚合

- **含义与关键内容：** 保存用户、模型、小时桶、使用分组、令牌、渠道、节点维度下的调用次数、用量额度、Token 和缓存 Token 汇总。
- **写入位置：** [model/usedata.go](../model/usedata.go) 的 `LogQuotaData` 先聚合到 `CacheQuotaData`，`SaveQuotaDataCache` 定期读取已有聚合行后更新或插入；消费日志结算路径根据统计开关调用聚合入口。
- **读取位置：** [controller/usedata.go](../controller/usedata.go)、[model/usedata_flow.go](../model/usedata_flow.go)、[model/usedata_rankings.go](../model/usedata_rankings.go) 用于看板、流向和排行；常见接口包括 `/api/data/` 和 `/api/data/self`。
- **主要关系与边界：** 用户、令牌和渠道维度与对应业务表关联；同一维度一小时内的多次调用会合并，不是一条请求一条记录。实际查询和写入表名是 `quota_data`。清理 `logs` 不会自动重算或删除本表。

### 6.4 `perf_metrics`：模型性能聚合

- **含义与关键内容：** 按模型、分组和时间桶保存请求数、成功数、总耗时、首 Token 耗时合计、输出 Token 数和生成耗时。
- **写入位置：** [pkg/perf_metrics/flush.go](../pkg/perf_metrics/flush.go) 把内存聚合通过 `UpsertPerfMetric` 写入；[model/perf_metric.go](../model/perf_metric.go) 提供模型定义、更新和查询。
- **读取位置：** [pkg/perf_metrics/metrics.go](../pkg/perf_metrics/metrics.go)、[controller/perf_metrics.go](../controller/perf_metrics.go) 和模型广场性能展示。
- **主要约束与生命周期：** `model_name + group + bucket_ts` 唯一；用于计算性能指标，不是完整请求轨迹，也不保存回答正文。按性能指标设置执行历史桶清理。

## 7. 异步模型任务与插件

### 7.1 `tasks`：通用异步生成任务

- **含义与关键内容：** 保存本地记录 ID、任务 ID、平台、用户、分组、渠道、预扣或结算额度、动作、状态、进度、提交与完成时间、失败原因、属性、内部数据和上游结果快照。
- **写入位置：** [relay/relay_task.go](../relay/relay_task.go) 提交异步任务；[service/task_polling.go](../service/task_polling.go) 轮询进度并更新结果；[service/task_billing.go](../service/task_billing.go) 参与最终计费和退款。
- **读取位置：** [model/task.go](../model/task.go) 的 `GetByTaskId`、`TaskGetAllUserTask`、`TaskGetAllTasks` 等；[controller/task.go](../controller/task.go)、任务查询和视频代理等功能。
- **主要关系与边界：** `user_id → users.id`，`channel_id → channels.id`；`properties`、`private_data`、`data` 是列，不是独立表。是否保存和暴露上游结果受任务和插件策略影响，不能推断所有任务都永久保留完整结果。
- **与聊天接口的区别：** 普通同步聊天请求不会因为调用 `/v1/chat/completions` 就生成一条本表任务记录。

### 7.2 `midjourneys`：Midjourney 专用任务

- **含义与关键内容：** 保存用户、Midjourney 任务 ID、动作、原始与英文提示词、状态、进度、时间、图片或视频地址、按钮、属性、失败原因，以及渠道和计费关联。
- **写入与读取：** [model/midjourney.go](../model/midjourney.go) 的 `Insert`、`Update`、`GetByMJId` 等；[controller/relay.go](../controller/relay.go)、[service/midjourney.go](../service/midjourney.go) 处理提交与查询；[controller/midjourney.go](../controller/midjourney.go) 提供任务管理，后台轮询更新状态。
- **主要关系：** 用户、执行渠道、计费渠道和令牌通过对应 ID 关联。与 `tasks` 共存，不应把全部 Midjourney 旧任务都当成 `tasks` 记录。
- **正文边界：** 本表确实保存 Midjourney 提示词；“聊天正文不默认入库”不能套用为“项目所有任务都不保存提示词”。

### 7.3 `task_plugins`：数据库插件版本

- **含义与关键内容：** 保存插件 key、API 版本、插件版本、源码、源码哈希、图标、启用状态、激活状态、时间和备注。`key + version` 唯一。
- **写入位置：** [controller/task_plugin.go](../controller/task_plugin.go) 的上传、激活、启停和版本删除，通过 [model/task_plugin.go](../model/task_plugin.go) 的 `SaveTaskPlugin`、`ActivateTaskPlugin`、`SetTaskPluginEnabled` 等保存。
- **读取位置：** `GetTaskPluginSyncSnapshot`、`ListActiveTaskPlugins` 等提供数据库覆盖版本；控制器的插件同步逻辑把版本交给运行时加载。
- **主要关系与边界：** 渠道设置中可绑定插件，任务内部数据可保存执行时的插件身份；数据库没有单独的渠道—插件关联表。内置文件插件不等于每个都必然在本表有记录；表名虽为 task plugins，具体支持能力仍由插件元数据和运行时决定。

## 8. 多节点、后台任务与维护

### 8.1 `system_instances`：运行节点与心跳

- **含义与关键内容：** 以 `node_name` 为主键，保存节点信息 JSON 文本、启动时间、最近心跳、创建和更新时间；节点信息包含运行环境、资源及各同步主题的应用状态。
- **写入位置：** [service/system_instance.go](../service/system_instance.go) 的节点报告逻辑通过 [model/system_instance.go](../model/system_instance.go) 的 `UpsertSystemInstance` 定期写入，当前报告间隔为 30 秒。
- **读取位置：** [controller/system_info.go](../controller/system_info.go) 的节点列表、失联节点清理，以及配置同步状态展示和判断。
- **边界：** 代表服务运行实例，不代表用户会话；节点在线状态根据最近心跳计算，而不是一个永久有效的布尔列。

### 8.2 `system_tasks`：后台作业与配置同步

- **含义与关键内容：** 保存后台任务 ID、类型、状态、活动任务键、输入 `payload`、执行中 `state`、结果、错误、执行节点和时间。
- **写入位置：** [service/system_task.go](../service/system_task.go) 的任务入队与运行器；[controller/system_task_handlers.go](../controller/system_task_handlers.go) 注册渠道测试、余额查询、模型更新、异步任务轮询和任务历史清理等处理器。
- **读取位置：** [controller/system_task.go](../controller/system_task.go) 提供创建、列表、详情和历史清理；[model/system_task.go](../model/system_task.go) 的 `CreateSystemTask`、`ClaimSystemTask`、`UpdateSystemTaskState`、`FinishSystemTask` 维护生命周期。
- **跨节点同步：** [model/system_sync_task.go](../model/system_sync_task.go) 的 `BumpSyncTopic` 为配置变化创建 `sync_options`、`sync_channels`、`sync_authz`、`sync_plugins` 等任务；各节点重新加载相关主题，并上报同步状态。
- **与业务任务的区别：** `tasks` 是用户提交给大模型的异步生成任务；本表是系统维护与同步作业。一条后台轮询作业可以处理多条用户任务，不是相互一一对应。

### 8.3 `system_task_locks`：后台执行租约

- **含义与关键内容：** 以任务类型 `type` 为主键，保存当前任务 ID、持有节点、租约到期时间和更新时间。
- **写入与读取：** [model/system_task.go](../model/system_task.go) 的 `acquireSystemTaskLock`、`RenewSystemTaskLock`、`ReleaseSystemTaskLock`、`ExpireStaleSystemTaskLocks`；[service/system_task.go](../service/system_task.go) 在领取和执行任务期间使用。
- **主要关系：** `task_id` 对应 `system_tasks.task_id`，通过类型维度租约协调相同类型后台任务的执行；状态更新还会检查执行者与租约是否仍有效。
- **边界：** 这是一张业务层租约表，不代表 MySQL 所有行锁或表锁；它也不是每次聊天调用都会新增的记录。

## 9. 条件迁移产生的表与历史对象

### 9.1 `options_pk_tmp`：配置表修复临时表

- 来源：[model/option_primary_key_migration.go](../model/option_primary_key_migration.go) 的 `repairOptionPrimaryKey`。
- 当旧 `options` 缺少正确的唯一键或主键时，用于写入按 key 去重后的配置并检查重建结果；随后通过表切换成为正式 `options`。
- 正常新安装不要求存在该表，也不是业务日常读写目标。成功切换后不会以临时名称继续承担配置读取；修复中断或遗留现场需要结合迁移结果判断。

### 9.2 `options_legacy_<时间戳>`：旧配置表备份

- 同一修复流程把旧 `options` 重命名为该格式，时间戳来自 `time.Now().UnixNano()`。
- 用来保留修复前的原始记录，可能包含重复 key；当前业务正常读取的是新的 `options`。
- 属于动态命名的历史备份，不是第 2 节固定迁移清单。是否存在以及有几张，取决于实际升级历史。

### 9.3 不应误记为额外 MySQL 业务表的对象

- `information_schema.*` 等是数据库系统目录，不是 New API 创建的业务表。
- `UserBase`、`TaskPrivateData`、`ChannelInfo`、`AuditOther`、`Properties`、响应 DTO 等可能是缓存、内嵌 JSON 或返回结构，不因存在结构体就拥有独立表。
- `group`、`auto`、插件 key 和渠道标签等常以字符串或 JSON 保存，当前没有统一的 `groups`、`token_groups`、`channel_plugin_bindings` 表。
- [bin/migration_v0.2-v0.3.sql](../bin/migration_v0.2-v0.3.sql) 和 [bin/migration_v0.3-v0.4.sql](../bin/migration_v0.3-v0.4.sql) 是历史数据调整脚本，涉及已有用户、令牌和能力表，不构成当前额外建表清单。
- 第三方插件自行接入的外部存储、手工创建的业务表、旧版本遗留表和数据库工具生成的对象，不在当前宿主程序固定表清单中。

## 10. 典型业务如何串联这些表

### 10.1 普通聊天接口 `/v1/chat/completions`

```text
tokens：校验 API Key、调用分组及限制
  → users：检查账号状态、所属分组和额度
  → options / 已加载设置：检查可用分组、价格及策略
  → abilities：查找本次分组与模型可用的渠道
  → channels：取得上游地址、密钥和模型映射
  → 请求上游大模型
  → users / tokens：钱包和令牌额度结算
    或 user_subscriptions + subscription_pre_consume_records：订阅计费
  → channels：累计渠道用量
  → logs：逐请求消费或错误记录
  → quota_data / perf_metrics：按设置聚合统计
```

这是逻辑依赖顺序，不代表每个请求都会对所有表执行 SQL。Redis、内存缓存、免费模型、信任额度、批量更新和功能开关会改变实际读写次数；通常也不会用一个数据库事务覆盖整个模型生成过程。

### 10.2 用户分组、令牌分组和渠道分组

```text
users.group：账号所属分组
  ＋ options 中的可用分组及特殊规则
  → 判断是否允许使用 tokens.group
  → 使用获准的调用分组匹配 abilities.group + abilities.model
  → 取得 channels 中的渠道
```

“测试用户组账号的 API Key 选择 VGS”可以成立，前提是账号有权使用 VGS，VGS 配置有效，而且有可用渠道支持所请求的模型。`prefill_groups` 和 `authz_roles` 不承担这里的路由分组含义。

### 10.3 订阅购买与消费

```text
subscription_plans：套餐定义
  → subscription_orders：购买订单
  → user_subscriptions：订单完成后获得订阅
  → subscription_pre_consume_records：请求预扣与退款识别
  → user_subscriptions：最终额度差额结算
  → logs：扣费明细
```

### 10.4 面板认证与审计

```text
users + 可选的 OAuth / Passkey / TOTP 相关表
  → auth_flows：跨步骤认证状态
  → user_sessions：登录成功后的会话
  → audit_logs：登录和安全操作事件

管理 API 个人访问令牌：user_access_tokens
管理权限：users.role → 代码内置角色与 casbin_rule 策略
角色元信息落库：authz_roles
模型调用 API Key：tokens
```

上述关系主要是业务引用，不等于数据库已经创建同名外键约束。当前大量关联采用 ID 或名称字段和显式查询维护，不能假设删除父记录会由数据库自动级联删除所有日志、订单或历史任务。

## 11. 如何核对运行中的 MySQL

以下均为只读查询。先选择实际数据库，再执行；不要把示例库名当成固定要求。

```sql
-- 当前连接的数据库。
SELECT DATABASE();

-- 实际表和视图清单，TABLE_TYPE 可区分对象类型。
SELECT TABLE_NAME, TABLE_TYPE, ENGINE, TABLE_COMMENT
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = DATABASE()
ORDER BY TABLE_NAME;

-- 按实际表名检查完整列定义和索引。
SHOW CREATE TABLE `users`;
SHOW CREATE TABLE `abilities`;
SHOW CREATE TABLE `logs`;
```

若配置了独立日志库，应在日志库中另外核对 `logs` 和 `audit_logs`。实际库里多出表时，先判断是否为历史迁移备份、旧版本残留或其他程序创建的对象；少表时先确认数据库连接、运行版本和主节点迁移是否完成，不能仅根据本清单认定可以直接删除或手工补表。
