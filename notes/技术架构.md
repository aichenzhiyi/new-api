# New API 技术架构概述

本文结合《技术架构.svg》和当前项目源码，按“客户端 → 统一接入 → 核心后端 → 模型转发 → 上游服务”的主线梳理系统，并补充数据存储、缓存及集群部署方式。

## 1. 整体定位

New API 是由 QuantumNous 维护的 AI API 网关。它对外提供统一的模型访问入口，对内连接 OpenAI、Claude、Gemini、DeepSeek、通义千问、智谱、Azure 等上游服务，同时提供用户管理、渠道管理、访问控制、限流、额度管理、计费和日志统计能力。

从代码组织看，项目采用**前后端分离开发、Go 后端按业务模块分层组织、可多实例部署**的架构。图中的路由、控制器、服务、模型和转发模块主要运行在同一个 Go 应用内，并不代表五个需要分别部署的微服务。生产构建会将前端静态文件嵌入 Go 程序，也可以根据部署需求安排独立的前端入口。

客户端通过网关调用模型时，使用网关地址和网关签发的 API 令牌；上游模型地址、凭据及协议差异由服务端渠道配置和适配器处理。

| 领域 | 当前项目使用的技术 | 主要用途 |

| 前端 | React 19、TypeScript、Rsbuild 2 | 管理控制台、用户界面和前端构建 |

| 日志数据库 | 默认复用主库；可单独配置 SQLite、MySQL、PostgreSQL 或 ClickHouse | 保存消费日志、错误及审计记录等 |

## 3. 架构图中的五层职责

### 3.1 客户端层：请求从哪里来

请求来源包括浏览器中的管理控制台、API / SDK 客户端，以及聊天应用、命令行工具和 Agent。管理人员通过页面配置用户、渠道和模型，业务应用则直接调用网关的模型接口。

网关支持普通 HTTP 请求、SSE 流式输出和 WebSocket。HTTPS 通常由入口反向代理或负载均衡器提供，再将请求转发给 Go 服务。

### 3.2 统一接入层：页面与 API 两类入口

**Web 控制台**位于 `web/`，提供渠道、模型、供应商、用户、令牌、日志和统计等功能。页面主要按 `routes`、`features`、`components` 组织；TanStack Query 管理服务端数据，Zustand 和 Context 分别承担应用状态及上下文，i18next 提供多语言。架构图中的“Context · i18n”是概括，当前状态管理还包括 Zustand。

**统一 API**由 Go 后端提供。常见入口包括：

| 接口类型 | 示例 | 用途 |
| --- | --- | --- |
| 控制台管理接口 | `/api/models/search`、`/api/vendors/search` | 查询、维护平台业务数据 |
| OpenAI 兼容接口 | `/v1/chat/completions`、`/v1/responses` | 聊天、工具调用及 Responses 请求 |
| Claude 兼容接口 | `/v1/messages` | 接收 Anthropic Messages 格式请求 |
| Gemini 兼容接口 | `/v1beta/models/...` | 接收 Gemini 格式请求 |
| 实时接口 | `/v1/realtime`、WebSocket 方式的 `/v1/responses` | 实时双向通信及对应协议交互 |

API / SDK 可以直接访问这些接口，无需经过 React 页面。实际可用的模型和能力取决于渠道配置、上游能力及协议转换支持情况。

### 3.3 核心后端层：平台业务与访问治理

后端以 `main.go` 为入口，初始化数据库、Redis、配置、缓存和后台任务，再启动 Gin 服务。主要目录职责如下：

| 目录 | 主要职责 |
| --- | --- |
| `router/` | 注册管理、模型转发、任务及页面等路由，组装中间件 |
| `middleware/` | 身份校验、权限检查、请求限流、渠道分发和请求上下文处理 |
| `controller/` | 接收请求、处理参数、编排业务调用并返回结果 |
| `service/` | 渠道选择、业务策略、计费结算、系统任务、节点同步等业务逻辑 |
| `model/` | GORM 数据模型、数据库访问、数据缓存及部分数据侧业务逻辑 |
| `setting/`、`common/` | 运行配置、公共工具、Redis 连接、日志和通用基础能力 |

这是职责划分，并非所有请求都严格逐层调用。例如部分控制器会直接调用 `model`，模型请求则进入专门的 `relay` 处理流程。

访问治理覆盖用户会话、API 令牌、个人访问令牌及管理权限等；管理授权使用 `service/authz/` 中的 Casbin。OAuth/OIDC、MFA、Passkeys 等能力属于平台账号体系，具体是否启用由配置决定。

### 3.4 模型转发层：选渠道、转协议、处理响应

转发能力主要位于 `middleware/distributor.go`、`controller/relay.go`、`service/channel_select.go` 和 `relay/`。

- **渠道选择**：根据请求模型、用户分组、渠道状态和请求约束筛选候选渠道，结合优先级、权重及渠道亲和关系完成选择。
- **负载与容错**：同一优先级内支持加权随机分发；失败后是否重试、切换渠道或进入其他优先级，由重试次数、错误策略和请求约束共同决定。配置模型不意味着已自动开启全部容错能力。
- **生命周期处理**：解析并校验请求，准备额度预扣，执行上游调用，处理流式或非流式响应，再进行结算、必要的退款和日志记录。
- **适配与转换**：通过 `relay/relay_adaptor.go` 选择适配器，由 `relay/channel/` 下的实现处理上游请求地址、认证方式、请求字段和响应差异。

项目还拆出了两个可独立构建的 Go 模块：

| 模块 | 边界与职责 |
| --- | --- |
| `relaykit/` | 协议 DTO，以及 OpenAI Chat、OpenAI Responses、Claude、Gemini 等协议间的请求、响应和流式事件转换；HTTP 收发、渠道选择、数据库和计费仍由宿主网关负责 |
| `tokenkit/` | 文本和图片 token 的计数或估算；请求解析、文件加载和计费由宿主负责 |

因此，架构图中的“Relay router → Handlers → Adapters”表达的是转发职责，实际源码中的渠道选择分布在中间件和服务层，协议转换也有独立模块承载。跨协议转换可能存在字段或能力差异，统一接入不代表所有厂商功能完全等价。

### 3.5 上游服务层：实际执行模型推理

OpenAI、DeepSeek、Gemini、Claude 等上游服务负责实际模型推理，New API 负责接入、选择、转发和平台管理。也可以通过相应适配器接入 Ollama 等自托管推理服务。

平台中的三个配置概念需要区分：

- **供应商**：模型的厂商归属、图标和展示分类等元数据。
- **模型元数据**：模型名称、描述、标签及供应商关联等管理信息。
- **渠道**：实际请求上游时使用的连接配置，包含服务类型、地址、凭据、支持模型、分组、优先级和权重等。

真正决定请求发往哪个上游地址的是渠道配置。同一个模型可以由多个渠道提供，也可以通过模型映射使用不同的上游模型名称。

## 4. 一次模型请求的处理链路

以调用已配置的 `deepseek-flash` 为例，客户端向网关发送 `POST /v1/chat/completions`，并携带网关 API 令牌：

```text
客户端 / SDK
  → 入口代理或负载均衡器（部署时可选）
  → Gin 路由、中间件：鉴权、限流、初始渠道分发
  → controller.Relay：请求解析、额度准备和重试编排
  → 渠道选择：确认本次使用的渠道和分组
  → relay 处理器、适配器：转换请求并调用上游
  → DeepSeek 或对应上游服务
  → 处理响应，按客户端协议返回结果或流式事件
  → 执行相应结算与日志记录
```

上述流程是职责概括。具体调用顺序会随接口类型、流式模式和插件路径有所不同；尤其在流式请求中，响应传输和统计处理会贯穿整个请求过程。

渠道筛选和重试主要可从 `service.SelectChannelForRequest`、`model.GetRandomSatisfiedChannel`、`controller.Relay`、`service.DecideRelayRetry` 继续追踪。

## 5. 数据存储、缓存与异步任务

### 5.1 数据库负责持久化

主库通过 `SQL_DSN` 配置，支持 SQLite、MySQL 和 PostgreSQL；未指定连接时默认使用 SQLite。主库保存用户、令牌、渠道、模型、供应商、额度和任务等数据。

日志通过 `LOG_SQL_DSN` 单独配置；未配置时复用主库。消费日志包含输入 token、输出 token、消耗额度、模型、渠道和耗时等信息，核心结构与写入逻辑位于 `model/log.go`。ClickHouse 可用于日志库，不作为主业务数据库。

### 5.2 Redis 与内存缓存降低热点访问开销

Redis 通过 `REDIS_CONN_STRING` 启用，主要承担：

- 用户、API 令牌、会话和部分业务信息缓存。
- 请求限流计数；多个节点使用同一个 Redis 时共享相应计数。
- 通过 Lua 原子操作检查、预扣缓存中的用户和令牌额度，并配合数据库持久化。
- 渠道亲和关系、部分任务分布式锁及 WebSocket 关闭事件广播。

本机内存缓存还用于渠道选择、配置读取和未启用 Redis 时的部分功能。Redis 不配置时应用仍可运行，但不同功能会改走数据库、本机内存或停用对应广播路径，集群共享语义也随之变化。

启用 Redis 并不会消除数据库写入。额度等业务数据仍需落库；启用 `BATCH_UPDATE_ENABLED` 后，部分增量更新会在进程中聚合后批量写入，这不等同于持久化消息队列。

### 5.3 后台任务与插件扩展

系统通过 Go 后台任务和数据库中的任务记录处理定时维护、异步任务轮询及结果结算等工作。JavaScript 插件位于 `plugins/tasks/`，通过 `pkg/jsplugin/` 和 moejs 运行时扩展模型、任务及请求处理能力。

当前架构不要求部署 Kafka 或 RabbitMQ。Redis Pub/Sub 用于特定即时通知，后台任务也有各自的数据库状态与执行机制。

## 6. 部署、集群与可观测性

### 6.1 开发与生产部署

开发时，前端通过 Bun 启动 Rsbuild 开发服务，并将相关 API 请求代理到 Go 后端。生产 Docker 构建先生成 `web/dist`，再由 Go 的 `//go:embed` 将静态文件嵌入程序；后端默认监听 3000 端口。

仓库中的 `docker-compose.yml` 提供应用、PostgreSQL 和 Redis 的组合部署示例，并包含 MySQL 和独立日志库的可选配置。Electron 则封装桌面窗口及本地后端进程，作为另一种交付形式。

### 6.2 多实例扩容

集群入口可使用 Nginx、HAProxy 或云负载均衡器，将请求分配给多个 New API 实例。应用实例连接同一个可写业务数据库入口；若需要共享 Redis 限流计数、缓存及相关协调功能，应连接同一个 Redis。

应用通过 `NODE_TYPE` 区分角色：仅 `NODE_TYPE=slave` 被识别为从节点，其他情况默认属于主节点。

| 角色 | 主要职责 |
| --- | --- |
| 主节点 | 处理正常业务请求，并执行主要数据库结构迁移、系统任务执行器及部分定时任务 |
| 从节点 | 同样处理模型调用和管理业务请求，跳过上述主节点专属工作 |

**应用主从角色不表示数据库读写分离。** 当前代码没有自动将所有写请求转发给主节点，从节点也会直接写共享数据库；请求落到哪个应用实例，由入口负载均衡配置决定。

各节点通过共享数据库中的变更版本以及周期性加载机制同步配置和本机缓存。角色由启动配置指定，从节点不会自动升级为主节点。

### 6.3 运行观测与容量边界

项目提供消费和错误日志、管理审计、请求性能统计、系统资源监控及实例状态上报，并可按配置开启性能分析能力。管理控制台据此展示运行状态和使用情况。

水平扩容主要增加应用层承载能力，整体吞吐量仍受到共享数据库、Redis、连接池、日志写入、网络及上游限额影响。架构图中的“Horizontal scale”表示支持多实例扩展，实际容量需要结合流量形态、部署资源和压测结果判断。
